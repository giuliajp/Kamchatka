# Импорт протокола в базу данных

[← Вернуться в основной README](../README.md)

Этот документ фиксирует правила задачи 2.2 — шаг 1 из 7.
Функция импорта, команда запуска и тесты будут добавлены следующими шагами.
Формат входных данных описан в [документации парсера](protocol-parser.md),
модели — в [описании предметной области](domain.md).

## Область применения

Импорт принимает полный итоговый JSON архивной гонки, полученный нашим PDF-парсером.
Схема БД и формат JSON остаются прежними. Исходный PDF и JSON сохраняются для сверки:
в БД переносится информация, для которой предусмотрены поля существующих моделей.

Штрафы относятся к участию в гонке. Время из протокола уже включает штрафы,
поэтому повторно к времени этапов и общему итогу они не прибавляются.

## Поиск существующих записей

| Модель | Ключ поиска и правило |
|---|---|
| `Race` | `year`; название, даты и место должны соответствовать источнику |
| `Stage` | гонка и `number` |
| `Discipline` | `code`; поддерживаются `ski_2`, `sled_8`, `sled_8plus` |
| `Participant` | нормализованные ФИО и год рождения |
| `RaceParticipant` | гонка и стартовый номер; дополнительно проверяется соответствие спортсмена и дисциплины |
| `Protocol` | этап и дисциплина |
| `StageResult` | протокол и участие в гонке |
| `Penalty` | участие в гонке; при повторном импорте сравниваются секунды, причина и пункт правил с учётом количества одинаковых записей |

Новые записи создаются, совпадающие используются повторно. Разные значения
переносимых полей у найденной записи считаются конфликтом. Если спортсмен уже
участвует в этой гонке под другим номером, это тоже конфликт.

Для поиска спортсмена удаляем пробелы по краям, последовательности пробелов
заменяем одним и сравниваем ФИО без учёта регистра. Дефисы сохраняем,
`е` и `ё` автоматически не объединяем. Поддерживаем порядок
«Фамилия Имя Отчество» и «Фамилия Имя»; в последнем случае отчество равно `null`.
Другой состав имени требует проверки до импорта.

Ноль совпадений по ФИО и году рождения означает создание спортсмена, одно —
использование найденного. Несколько совпадений приводят к ошибке без автоматического
объединения людей. Фото, биография и прочие поля вне источника сохраняются у
существующего спортсмена.

Дисциплины обычно уже созданы миграцией `0002`. Недостающие записи из трёх
поддерживаемых дисциплин создаются по тому же справочнику: код, название,
снаряжение, границы числа собак и порядок сортировки. Найденную дисциплину
не переименовываем по заголовку PDF. Неизвестный код — ошибка.

## Соответствие полей

| JSON | Модель и поле | Правило |
|---|---|---|
| `race.name`, `year`, `start_date`, `end_date`, `location` | соответствующие поля `Race` | даты переводятся из ISO-строк в `date` |
| `stages[].number`, `distance_km` | `Stage.number`, `distance_km` | один этап на номер внутри гонки |
| `participants[].full_name`, `birth_year` | ФИО и `Participant.birth_year` | имя разбирается по правилам поиска спортсмена |
| `start_number`, `region`, `discipline_code` | `RaceParticipant.start_number`, `region`, `discipline_id` | участие связывается с гонкой, спортсменом и дисциплиной |
| `protocol_metadata` | `Protocol.weather`, `chief_judge`, `chief_secretary` | метаданные документа переносятся во все создаваемые протоколы |
| `source_filename` | `Protocol.source_filename` | сохраняется имя исходного PDF из JSON, а не имя JSON-файла |
| `stage_results[].stage_number` | этап, к которому относится `Protocol` | протокол выбирается также по дисциплине участника |
| `stage_results[].status`, `final_time_seconds` | `StageResult.status`, `final_time_seconds` | явные результаты переносятся; ожидаемые пустые результаты пропускаются по правилам ниже |
| `summary.source_place` | `StageResult.place` последнего этапа | переносится только для финишировавшего участника; места после предыдущих этапов не вычисляются из итогового места |
| `penalties[].seconds`, `rule_reference`, `raw_note` | `Penalty.seconds`, `rule_reference`, `reason` | каждый штраф связывается с `RaceParticipant` |

Для каждой пары «этап — используемая в JSON дисциплина» создаётся протокол,
в том числе если на этом этапе у части участников нет результата.

Чистое время, число собак, координаты КП, названия и даты отдельных этапов
в JSON отсутствуют. У новых записей соответствующие поля остаются пустыми;
значения существующих записей вне импортируемых полей сохраняются.
Примечание о штрафе относится к гонке и переносится в `Penalty.reason`.
Поле `StageResult.note` остаётся пустым: отдельного примечания к этапу в JSON нет.

Для финишировавшего участника `summary.total_time_seconds` используется для проверки
суммы времён этапов, `summary.total_penalty_seconds` — для проверки суммы записей `Penalty`
при любом общем статусе.
Отдельных колонок для этих сумм в БД нет. Исходные текстовые поля и итоговое место
нефинишировавшего участника сохраняются в JSON; последнее не переносится в место
на том этапе, где участник выбыл.

## Статусы

Новая архивная гонка и её этапы получают `finished`. Новая гонка создаётся с
`is_current=False`; импорт архива не переключает выбранную текущую гонку.

Новые протоколы создаются как черновики: `status=preliminary`,
`published_at=null`, `finalized_at=null`, `finalized_by=null`.
Дата загрузки и дата окончания гонки не подменяют дату утверждения судьями.
Публикация и утверждение относятся к задаче 3.3.
При повторной загрузке совпадающих данных уже установленные признаки публикации
и утверждения сохраняются.

Статус результата этапа копируется из `stage_results[].status`:
`finished`, `dnf`, `dns` или `dsq`. Он задаётся явно при создании `StageResult`.
У `finished` должно быть положительное итоговое время, у остальных статусов — `null`.
`net_time_seconds` остаётся `null`, поскольку чистого времени нет в источнике.

Общий статус участия в гонке отличается от статуса отдельного этапа.
В существующем `RaceParticipantStatus` нет `dns`, поэтому используется такое соответствие:

| `summary.status` | `RaceParticipant.status` |
|---|---|
| `finished` | `finished` |
| `dnf` | `dnf` |
| `dsq` | `dsq` |
| `dns`, при этом есть завершённый этап или явный DNF | `dnf`: участник начал гонку и не завершил её |
| `dns`, при этом нет ни завершённых этапов, ни явного DNF | `registered`: участник заявлен, но не начал гонку |

У участницы №10 исходный общий статус в JSON остаётся `dns`, результат третьего
этапа в БД — `dns`, а `RaceParticipant.status` — `dnf`, поскольку первые два этапа
она завершила. Это разные поля с разным смыслом. Статус участия в гонке нельзя
выдавать за буквальную копию официального общего статуса из JSON.

## Пустые этапы после DNF/DNS

Результаты рассматриваются по возрастанию номера этапа. Пустой результат
пропускается при одновременном выполнении условий:

- на одном из предыдущих этапов этого участника уже встречался явный `dnf` или `dns`;
- `raw_result` содержит нулевую длительность, `status` и `final_time_seconds` равны `null`;
- у результата нет предупреждения.

Для такого элемента `StageResult` не создаётся. Участник и его участие в гонке
сохраняются. Явные DNF/DNS/DSQ также сохраняются как результаты этапов.
Пустой результат без предшествующего DNF/DNS, неизвестный статус или противоречивые
поля приводят к ошибке, а не к молчаливому пропуску.

Будущий API результатов должен строить таблицу по полному списку `RaceParticipant`
нужной дисциплины и присоединять имеющиеся результаты этапов. Отсутствие результата
показывается как «—». Запрос только к `StageResult` не должен становиться списком
участников протокола: иначе выбывшие участники исчезнут с последующих этапов.

## Проверки и повторный импорт

До сохранения проверяются структура документа, известные статусы и дисциплины,
уникальность участников и этапов, набор результатов каждого участника,
корректность дат, времени, мест и положительных длительностей штрафов.
Общее время финишировавшего должно совпадать с суммой итоговых времён этапов.
`summary.total_penalty_seconds` должно совпадать с суммой распознанных штрафов;
при пустом списке штрафов оно равно `0`.

Предупреждения результатов и штрафов требуют проверки данных до импорта.
Отсутствие необязательных погоды и подписей допускается: поля протокола остаются
пустыми, соответствующие предупреждения передаются в отчёт.

Сохранение всего документа выполняется одной транзакцией. При любой ошибке
откатываются все изменения этого запуска. Ошибка должна содержать контекст:
участника, этап, поле либо ключ конфликтующей записи.

Повторный импорт совпадающих данных использует существующие записи и не создаёт
дублей, в том числе штрафов. Сравнение учитывает значения полей, а не порядок
участников, этапов и штрафов в JSON. Если уже есть отличающиеся результаты или
метаданные источника, импорт прекращается с ошибкой. Существующие строки,
дополнительные результаты и штрафы не удаляются автоматически ради совпадения.
Исправление ранее сохранённых результатов и штрафов выполняется отдельным
процессом с журналом правок, описанным в задаче 3.3.
