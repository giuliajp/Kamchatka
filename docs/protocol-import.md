# Импорт протокола в базу данных

[← Вернуться в основной README](../README.md)

Этот документ фиксирует правила задачи 2.2. Выполнены шаги 1–6 из 7:
описаны правила, добавлены подготовка основных записей и перенос протоколов,
результатов и штрафов, проверены повторная загрузка, конфликты и откат.
Добавлены команда запуска с отчётом и тесты на PostgreSQL.
Финальная загрузка архива остаётся шагом 7.
Формат входных данных описан в [документации парсера](protocol-parser.md),
модели — в [описании предметной области](domain.md).

## Область применения

Импорт принимает полный итоговый JSON архивной гонки, полученный нашим PDF-парсером.
Схема БД и формат JSON остаются прежними. Исходный PDF и JSON сохраняются для сверки:
в БД переносится информация, для которой предусмотрены поля существующих моделей.

Штрафы относятся к участию в гонке. Время из протокола уже включает штрафы,
поэтому повторно к времени этапов и общему итогу они не прибавляются.

## Запуск команды

Команда находится в `backend/scripts/import_protocol.py`. Примеры выполняются
из корня проекта с активированным виртуальным окружением. Зависимости,
PostgreSQL и настройки `backend/.env` подготавливаются по
[инструкции бэкенда](../backend/README.md). Переменные окружения имеют приоритет
над значениями из `backend/.env`. Запущенный API для импорта не требуется.

Применить миграции и получить JSON из PDF:

```bash
python -m alembic -c backend/alembic.ini upgrade head
python backend/scripts/parse_protocol.py --pdf docs/Total_result_Avacha-2026.pdf --output .cache/protocols/avacha-2026.json
```

Загрузить готовый JSON в настроенную БД:

```bash
python backend/scripts/import_protocol.py --json .cache/protocols/avacha-2026.json
```

Справка:

```bash
python backend/scripts/import_protocol.py --help
```

`--json` — обязательный путь к входному файлу. Путь может быть абсолютным или
относительным к текущему каталогу; пути с пробелами нужно заключать в кавычки.
Файл читается как UTF-8, в том числе с BOM. Исходный JSON не изменяется.
Для справки, проверки аргументов и чтения файла подключение к БД не требуется.

Команда вызывает `import_protocol` в одной транзакции и печатает отчёт только
после успешного `commit`. При ошибке проверки, конфликтах, ошибке записи или
фиксации транзакции изменения импорта откатываются. Соединения закрываются
при завершении команды.

В отчёте показываются id гонки, число созданных записей каждой модели
и число пропущенных пустых результатов после DNF/DNS. Для чистой БД с уже
заполненным миграцией справочником дисциплин пример выглядит так:

```text
Импорт завершён. ID гонки: 1
Создано записей:
  Гонки: 1
  Этапы: 6
  Дисциплины: 0
  Спортсмены: 21
  Участия в гонке: 21
  Протоколы: 18
  Результаты этапов: 118
  Штрафы: 3
Пропущено пустых результатов после DNF/DNS: 8
```

Счётчики относятся к этому запуску: найденные совпадающие записи в них
не включаются. При совпадающем повторном импорте все счётчики равны нулю,
выводится сообщение «Все записи уже существуют и совпадают с JSON»,
число пропусков остаётся равным восьми для исходного архива 2026.
Предупреждения об отсутствии необязательных метаданных печатаются в `stderr`.

Коды завершения: `0` — успешный импорт, включая совпадающий повтор;
`1` — ошибка файла, данных, настроек или БД; `2` — неверные аргументы команды.
Ошибки выводятся в `stderr` без traceback; для ошибок проверки указывается путь
к полю. В сообщениях об ошибках БД не печатаются строка подключения и пароль.

Проверки команды находятся в `backend/tests/test_import_protocol_cli.py`.
Рабочая локальная загрузка архива 2026 остаётся шагом 7.

## Подготовка основных записей

Функция `prepare_protocol_import(session, document)` находится в
`backend/app/services/protocol_import.py`. Она принимает словарь из JSON,
проверяет поля основных сущностей и статусы, создаёт или находит необходимые
записи и возвращает `PreparedProtocolImport`: гонку, этапы по номеру,
дисциплины по коду, участия по стартовому номеру и счётчики созданных записей.

Входные поля проверяются схемами из `backend/app/schemas/protocol_import.py`.
Эта функция проверяет данные гонки, этапов и участников. Для переноса всего
документа с полной проверкой результатов и штрафов используется `import_protocol`.

Транзакцией управляет вызывающий код: функцию нужно вызывать внутри
`async with session.begin()`. Она выполняет `flush` для получения id записей,
а завершение или откат транзакции остаётся вызывающему коду. Это позволит
переносить все сущности полного протокола в одной транзакции.

Проверки этой части на PostgreSQL находятся в `backend/tests/test_import_protocol.py`.

## Перенос полного протокола

Функция `import_protocol(session, document)` находится в том же сервисе.
До любых записей в БД документ проверяется схемой `CompleteProtocolImportData`:
исходные времена должны соответствовать статусам и числу секунд, общий итог
финишировавшего — сумме этапов, а сумма штрафов — списку `penalties`.

Затем функция подготавливает основные записи, создаёт протоколы для всех пар
«этап — дисциплина», переносит явные результаты и штрафы участников.
Ожидаемые пустые результаты после DNF/DNS пропускаются. Место из общего итога
переносится только в результат последнего этапа финишировавшего участника.

Возвращается `ProtocolImportResult`: id гонки, счётчики созданных записей,
число пропущенных результатов и предупреждения об отсутствии необязательных
метаданных. Существующие совпадающие записи используются повторно;
уже установленные признаки публикации и утверждения протоколов сохраняются.

Как и подготовку основных записей, эту функцию нужно вызывать внутри
`async with session.begin()`. Она не выполняет самостоятельный `commit`.
Без активной транзакции вызов отклоняется до обращения к БД.
Внутри транзакции функция открывает `SAVEPOINT`: при ошибке отменяется весь
текущий импорт, даже если исключение перехвачено внутри внешнего блока.
Данные, сохранённые вызывающим кодом до импорта, остаются в его транзакции;
после устранения причины ошибки импорт можно повторить в той же сессии.
Успешный вызов также не фиксирует внешнюю транзакцию: ошибка вызывающего кода
до выхода из `session.begin()` откатит и импорт.
Команда запуска выше управляет этой внешней транзакцией.

## Поиск существующих записей

| Модель | Ключ поиска и правило |
|---|---|
| `Race` | `year`; название, даты и место должны соответствовать источнику |
| `Stage` | гонка и `number` |
| `Discipline` | `code`; поддерживаются `ski_2`, `sled_8`, `sled_8plus` |
| `Participant` | нормализованные ФИО и год рождения |
| `RaceParticipant` | гонка и стартовый номер; дополнительно проверяется соответствие спортсмена и дисциплины |
| `Protocol` | этап и дисциплина |
| `StageResult` | протокол и участие в гонке |
| `Penalty` | участие в гонке; при повторном импорте сравниваются секунды, причина и пункт правил с учётом количества одинаковых записей |

Новые записи создаются, совпадающие используются повторно. Разные значения
переносимых полей у найденной записи считаются конфликтом. Если спортсмен уже
участвует в этой гонке под другим номером, это тоже конфликт.

Для поиска спортсмена удаляем пробелы по краям, последовательности пробелов
заменяем одним и сравниваем ФИО без учёта регистра. Дефисы сохраняем,
`е` и `ё` автоматически не объединяем. Поддерживаем порядок
«Фамилия Имя Отчество» и «Фамилия Имя»; в последнем случае отчество равно `null`.
Другой состав имени требует проверки до импорта.

Ноль совпадений по ФИО и году рождения означает создание спортсмена, одно —
использование найденного. Несколько совпадений приводят к ошибке без автоматического
объединения людей. Фото, биография и прочие поля вне источника сохраняются у
существующего спортсмена.

Дисциплины обычно уже созданы миграцией `0002`. Недостающие записи из трёх
поддерживаемых дисциплин создаются по тому же справочнику: код, название,
снаряжение, границы числа собак и порядок сортировки. Найденную дисциплину
не переименовываем по заголовку PDF. Неизвестный код — ошибка.

## Соответствие полей

| JSON | Модель и поле | Правило |
|---|---|---|
| `race.name`, `year`, `start_date`, `end_date`, `location` | соответствующие поля `Race` | даты переводятся из ISO-строк в `date` |
| `stages[].number`, `distance_km` | `Stage.number`, `distance_km` | один этап на номер внутри гонки |
| `participants[].full_name`, `birth_year` | ФИО и `Participant.birth_year` | имя разбирается по правилам поиска спортсмена |
| `start_number`, `region`, `discipline_code` | `RaceParticipant.start_number`, `region`, `discipline_id` | участие связывается с гонкой, спортсменом и дисциплиной |
| `protocol_metadata` | `Protocol.weather`, `chief_judge`, `chief_secretary` | метаданные документа переносятся во все создаваемые протоколы |
| `source_filename` | `Protocol.source_filename` | сохраняется имя исходного PDF из JSON, а не имя JSON-файла |
| `stage_results[].stage_number` | этап, к которому относится `Protocol` | протокол выбирается также по дисциплине участника |
| `stage_results[].status`, `final_time_seconds` | `StageResult.status`, `final_time_seconds` | явные результаты переносятся; ожидаемые пустые результаты пропускаются по правилам ниже |
| `summary.source_place` | `StageResult.place` последнего этапа | переносится только для финишировавшего участника; места после предыдущих этапов не вычисляются из итогового места |
| `penalties[].seconds`, `rule_reference`, `raw_note` | `Penalty.seconds`, `rule_reference`, `reason` | каждый штраф связывается с `RaceParticipant` |

Для каждой пары «этап — используемая в JSON дисциплина» создаётся протокол,
в том числе если на этом этапе у части участников нет результата.

Чистое время, число собак, координаты КП, названия и даты отдельных этапов
в JSON отсутствуют. У новых записей соответствующие поля остаются пустыми;
значения существующих записей вне импортируемых полей сохраняются.
Примечание о штрафе относится к гонке и переносится в `Penalty.reason`.
Поле `StageResult.note` остаётся пустым: отдельного примечания к этапу в JSON нет.

Для финишировавшего участника `summary.total_time_seconds` используется для проверки
суммы времён этапов, `summary.total_penalty_seconds` — для проверки суммы записей `Penalty`
при любом общем статусе.
Отдельных колонок для этих сумм в БД нет. Исходные текстовые поля и итоговое место
нефинишировавшего участника сохраняются в JSON; последнее не переносится в место
на том этапе, где участник выбыл.

## Статусы

Новая архивная гонка и её этапы получают `finished`. Новая гонка создаётся с
`is_current=False`; импорт архива не переключает выбранную текущую гонку.

Новые протоколы создаются как черновики: `status=preliminary`,
`published_at=null`, `finalized_at=null`, `finalized_by=null`.
Дата загрузки и дата окончания гонки не подменяют дату утверждения судьями.
Публикация и утверждение относятся к задаче 3.3.
При повторной загрузке совпадающих данных уже установленные признаки публикации
и утверждения сохраняются.
Если хотя бы один протокол гонки опубликован или утверждён, импорт допускает
только полностью совпадающую повторную загрузку без создания записей.
Добавление недостающих результатов, штрафов или других записей в такой архив
требует отдельной процедуры правок. Совместимые недостающие записи в неопубликованном
архиве с предварительными протоколами можно дополнить импортом.

Статус результата этапа копируется из `stage_results[].status`:
`finished`, `dnf`, `dns` или `dsq`. Он задаётся явно при создании `StageResult`.
У `finished` должно быть положительное итоговое время, у остальных статусов — `null`.
`net_time_seconds` остаётся `null`, поскольку чистого времени нет в источнике.

Общий статус участия в гонке отличается от статуса отдельного этапа.
В существующем `RaceParticipantStatus` нет `dns`, поэтому используется такое соответствие:

| `summary.status` | `RaceParticipant.status` |
|---|---|
| `finished` | `finished` |
| `dnf` | `dnf` |
| `dsq` | `dsq` |
| `dns`, при этом есть завершённый этап или явный DNF | `dnf`: участник начал гонку и не завершил её |
| `dns`, при этом нет ни завершённых этапов, ни явного DNF | `registered`: участник заявлен, но не начал гонку |

У участницы №10 исходный общий статус в JSON остаётся `dns`, результат третьего
этапа в БД — `dns`, а `RaceParticipant.status` — `dnf`, поскольку первые два этапа
она завершила. Это разные поля с разным смыслом. Статус участия в гонке нельзя
выдавать за буквальную копию официального общего статуса из JSON.

## Пустые этапы после DNF/DNS

Результаты рассматриваются по возрастанию номера этапа. Пустой результат
пропускается при одновременном выполнении условий:

- на одном из предыдущих этапов этого участника уже встречался явный `dnf` или `dns`;
- `raw_result` содержит нулевую длительность, `status` и `final_time_seconds` равны `null`;
- у результата нет предупреждения.

Для такого элемента `StageResult` не создаётся. Участник и его участие в гонке
сохраняются. Явные DNF/DNS/DSQ также сохраняются как результаты этапов.
Пустой результат без предшествующего DNF/DNS, неизвестный статус или противоречивые
поля приводят к ошибке, а не к молчаливому пропуску.

Будущий API результатов должен строить таблицу по полному списку `RaceParticipant`
нужной дисциплины и присоединять имеющиеся результаты этапов. Отсутствие результата
показывается как «—». Запрос только к `StageResult` не должен становиться списком
участников протокола: иначе выбывшие участники исчезнут с последующих этапов.

## Проверки и повторный импорт

До сохранения проверяются структура документа, известные статусы и дисциплины,
уникальность участников и этапов, набор результатов каждого участника,
корректность дат, времени, мест и положительных длительностей штрафов.
Общее время финишировавшего должно совпадать с суммой итоговых времён этапов.
`summary.total_penalty_seconds` должно совпадать с суммой распознанных штрафов;
при пустом списке штрафов оно равно `0`.

Предупреждения результатов и штрафов требуют проверки данных до импорта.
Отсутствие необязательных погоды и подписей допускается: поля протокола остаются
пустыми, соответствующие предупреждения передаются в отчёт.

Сохранение всего документа выполняется одной транзакцией. При любой ошибке
откатываются все изменения этого запуска. Ошибка должна содержать контекст:
участника, этап, поле либо ключ конфликтующей записи.

Повторный импорт совпадающих данных использует существующие записи и не создаёт
дублей, в том числе штрафов. Сравнение учитывает значения полей, а не порядок
участников, этапов и штрафов в JSON. Если уже есть отличающиеся результаты или
метаданные источника, импорт прекращается с ошибкой. Существующие строки,
дополнительные результаты и штрафы не удаляются автоматически ради совпадения.
Поскольку JSON описывает всю гонку, дополнительные этапы, участия и протоколы,
отсутствующие в источнике, также считаются конфликтом. Проверяется, что существующие
результаты относятся к нужной гонке и дисциплине участника; результат в чужом
протоколе не игнорируется. Эти проверки не затрагивают самостоятельные данные
других гонок и неиспользуемые записи справочника дисциплин.
Исправление ранее сохранённых результатов и штрафов выполняется отдельным
процессом с журналом правок, описанным в задаче 3.3.

Тесты на PostgreSQL сравнивают все поля сохранённых записей, включая id и даты
изменения, до и после повторной загрузки. Отдельно проверяются поздний конфликт
штрафов после сохранения результатов, ошибка ограничения БД, повторный запуск
после отката в той же сессии и откат внешней транзакции вызывающим кодом.

## Проверка тестами на PostgreSQL

Сценарии импорта находятся в `backend/tests/test_import_protocol.py`,
проверки команды — в `backend/tests/test_import_protocol_cli.py`.
Тесты записи используют PostgreSQL из настроек бэкенда. Для каждого теста
создаётся отдельная временная схема, которая удаляется после выполнения.

Из корня проекта в активированном окружении:

```bash
python -m pytest -c backend/pytest.ini backend/tests/test_import_protocol.py backend/tests/test_import_protocol_cli.py -q
```

| Требование шага 6 | Что проверяется |
|---|---|
| Исходный протокол | Разбор реального PDF 2026 и полный импорт: 21 участие, 18 протоколов, 118 результатов, 3 штрафа и 8 пропусков; сохранённые времена не увеличиваются на сумму штрафов |
| Повторная загрузка | Отсутствие дублей, сохранение id, дат изменения, признаков публикации и утверждения; порядок элементов JSON не влияет на результат |
| Поиск спортсмена | Повторное использование по ФИО и году рождения, в том числе из другой гонки; нормализация пробелов и регистра; отдельные карточки при отличающихся или неизвестных годах рождения, отчествах, `е`/`ё` и дефисах |
| Ошибки данных | Отказ при неоднозначном совпадении спортсмена, некорректном JSON и противоречащих данным БД значениях |
| Откат | Отмена всего импорта при позднем конфликте, ошибках записи и `commit`, откате внешней транзакции; возможность исправить причину и повторить импорт в той же сессии |

Дополнительно проверяются полный импорт DNS и DSQ, пропуск пустых этапов после
DNS, сохранение явных статусов и отсутствие итогового места у нефинишировавшего.
Импорт другой гонки повторно использует спортсменов, сохраняя уже существующие
участия, протоколы, результаты, штрафы, карточки спортсменов и текущую гонку.

Все тесты бэкенда запускаются командой:
